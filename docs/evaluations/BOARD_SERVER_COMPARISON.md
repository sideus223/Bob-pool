# 실제 Android 기기의 게시판 조회 방식 전후 비교

이 문서는 게시글 1,000개 조건의 첫 비교입니다. 데이터가 적을 때의 차이까지 확인한 후속 측정은 [게시글 수에 따른 실서버 비교](BOARD_SERVER_SCALE_COMPARISON.md)에 함께 정리했습니다.

2026-10-14에 같은 휴대폰과 실제 Firestore 서버에서 합성 게시글 1,000개를 조회했습니다. 기존 전체 구독 방식의 첫 서버 응답과 현재 20개 페이지 조회를 비교한 결과, **조회 응답 시간의 중앙값이 9,734.206ms에서 484.740ms로 95.020% 감소**했습니다.

이 결과는 구버전의 조회 코드를 같은 SDK에서 재현해 비교한 값입니다. 휴대폰에 설치돼 있던 옛 APK 전체와 현재 앱 전체를 비교한 결과는 아닙니다.

<br><br><br>





## 비교 조건

| 항목 | 조건 |
|---|---|
| 기기 | Samsung SM-S931N, Android 16 / API 36, USB 연결 |
| 실행 앱 | 동일한 Flutter profile APK, Android arm64, `1.0.0+7` |
| 서버 | 실제 Firestore 기본 데이터베이스, `asia-northeast3` 서울 |
| 인증 | 동일한 Firebase Authentication 로그인 세션 |
| 데이터 | 운영 게시글과 분리한 합성 게시글 1,000개, 모두 `deleted=false` |
| 게시글 내용 | 문서마다 서로 다른 결정적 ASCII 문자열 1,024자, 고유 생성 시각 |
| 기존 방식 | `4848f33` 직전 코드의 `createdAt` 내림차순 전체 구독, 첫 비캐시 서버 스냅샷까지 측정 |
| 현재 방식 | `deleted=false`, `createdAt` 내림차순·문서 ID 정렬, `limit(20)`, `Source.server` |
| 반복 | 총 24쌍·48회. 앞의 4쌍을 예열로 제외하고 각 방식 20회 집계 |
| 실행 순서 | 홀수 쌍은 기존→현재, 짝수 쌍은 현재→기존. 각 조회 후 1초 간격 |
| 캐시 | 디스크 영속성 비활성화, 48회 모두 비캐시 응답. SDK 메모리 최적화는 별도 통제하지 않음 |
| 오류 | 0회. 모든 기존 응답 1,000개, 현재 응답 20개 확인 |

운영 규칙은 무제한 게시글 쿼리를 차단하므로, 승인받은 별도 테스트 경로에만 로그인한 소유자가 읽을 수 있는 1시간 만료 규칙을 적용했습니다. 테스트 경로의 클라이언트 쓰기는 금지했습니다. 운영 게시글은 복사하거나 수정하지 않았습니다.

## 결과

시간은 휴대폰에서 쿼리를 시작한 뒤 SDK가 결과를 반환할 때까지의 경과 시간입니다. 네트워크·SDK 처리·첫 스냅샷 전달을 포함하며, 서버 내부 연산 시간만 분리한 값은 아닙니다.

| 지표 | 기존 전체 구독 | 현재 첫 페이지 조회 |
|---|---:|---:|
| 최초 반환 문서 수 | 1,000개 | 20개 |
| 조회 응답 중앙값 | 9,734.206ms | 484.740ms |
| 조회 응답 p95 | 10,821.628ms | 527.585ms |
| 조회 응답 평균 | 9,867.802ms | 488.781ms |
| 조회 응답 최소 | 9,170.142ms | 465.064ms |
| 조회 응답 최대 | 11,246.909ms | 528.051ms |
| 응답 후 모델 변환 중앙값 | 1.802ms | 0.096ms |

- 최초 반환 문서 수 감소율: `(1,000 - 20) / 1,000 × 100 = 98%`
- 조회 응답 중앙값 감소율: `(9,734.206 - 484.740) / 9,734.206 × 100 = 95.020%`
- 예열을 제외한 **20쌍 모두 현재 방식의 응답 시간이 짧았습니다.**

중앙값은 정렬한 20개 값 중 가운데 두 값의 평균이며, p95는 `ceil(20 × 0.95)`번째 값입니다. 전체 이벤트를 검사해 순서·예열 구분·문서 수·비캐시 응답·완료 여부가 맞을 때만 통계를 생성했습니다. 서로 다른 지표의 중앙값을 더해 합산 시간으로 해석하지 않습니다.

<br><br><br>





## 해석 범위

**“합성 게시글 1,000개 조건의 실제 기기·실서버 비교에서 첫 조회 응답 중앙값을 약 95.0% 줄였다”**고 설명할 수 있습니다.

한 기기와 한 세션에서 측정했으며 네트워크 대역폭·다른 앱의 실행 상태는 통제하지 않았습니다. 실제 운영 게시글 4개로 앞서 측정한 현재 버전의 중앙값 524.526ms와는 데이터 조건과 측정 세션이 다릅니다. [현재 버전 단독 측정](BOARD_SERVER_LATENCY.md)의 수치와 서로 나눠 개선율을 계산하지 않습니다.

기존 구독은 첫 서버 응답을 받은 뒤 종료했습니다. 이후 실시간 변경 알림, 카드의 댓글 수 구독, 전체 화면 렌더링 시간, 모든 페이지를 끝까지 읽는 시간, 과금액은 비교하지 않았습니다. 현재 방식은 우선 20개를 받으므로 전체 1,000개를 모두 받은 상태와 제공하는 데이터 범위가 다릅니다. **전체 앱 속도가 95% 개선됐다는 의미는 아닙니다.**

## 측정 자료와 재현

- [통계·쌍별 측정값·정리 검증 결과](board-server-comparison-2026-10-14.json)
- [개인정보 없는 원시 이벤트 49개](board-server-comparison-events-2026-10-14.json): 조회 48개, 완료 1개
- [독립 비교용 Flutter 진입점](../../tools/board_query_comparison_main.dart)
- [중앙값·p95·전후 감소율 집계 스크립트](../../tools/summarize_board_comparison.ps1)

비교용 진입점은 일반 앱과 분리했습니다. 실제 재측정에는 관리자 권한으로 별도 합성 데이터를 준비하고 제한된 테스트 읽기 권한을 설정하는 과정이 필요합니다. 만료·소유자 제한 규칙의 허용·차단 조건은 로컬 Firestore Emulator에서 9개 검사를 통과한 뒤 서버에 적용했습니다.

```powershell
flutter build apk --profile --target-platform android-arm64 --target=tools/board_query_comparison_main.dart --dart-define=DEMO_MODE=false --dart-define=BOARD_COMPARE_RUN_ID=<별도-테스트-ID> --build-number=7 --no-pub
./tools/summarize_board_comparison.ps1 -InputPath <BOARD_COMPARE-로그-경로> -OutputPath <통계-JSON-경로>
```

측정 APK는 당시 보관한 임시 진입점으로 빌드했습니다. 현재 `tools/` 진입점은 동일한 두 조회 방식에 게시글 수 선택 기능을 추가한 버전이며, 기본값은 1,000개입니다. 합성 본문은 각 문서 `i`와 구간 `segment=0..15`에 대해 `SHA256("board-fixture-v1:{i}:{segment}")`의 64자 hex 값을 이어 붙였습니다. 문서 제목·필드·시각까지 포함한 fixture 지문과 APK 지문을 결과 JSON에 보관했습니다. 집계 스크립트의 계산은 감소율이 50%인 별도 입력으로 검증했습니다.

## 측정 후 정리

합성 문서 1,000개를 삭제하고 해당 경로에 남은 문서가 **0개**임을 확인했습니다. 원래 서버 규칙 릴리스로 복원한 뒤 규칙 소스 SHA-256이 측정 전 백업과 동일한지도 확인했습니다. 만료된 임시 규칙에 의존해 정리를 대신하지 않았습니다.

휴대폰에는 일반 `lib/main.dart`의 profile 빌드 `1.0.0+7`을 같은 서명으로 덮어 설치했습니다. 앱 데이터 삭제 없이 로그인과 정상 화면이 유지되고, 새 프로세스에서 비교·반복 측정 로그가 발생하지 않는 것을 확인했습니다. 공개 측정 자료에는 게시글 본문, 계정 식별자, 이메일, 인증 토큰을 포함하지 않았습니다.
