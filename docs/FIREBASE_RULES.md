# Firestore 권한과 검증

`firebase/firestore.rules`는 현재 Flutter 클라이언트가 쓰는 문서 구조를 기준으로 작성했다.
로컬 테스트는 [Firebase 공식 Emulator / Rules Unit Testing 문서](https://firebase.google.com/docs/firestore/security/test-rules-emulator)를 따른다.
실제 프로젝트의 기존 규칙과 새 규칙의 에뮬레이터 결과, 실제 배포 여부는 구분한다.

<br><br><br>





## 권한 정책

| 작업 | 허용 범위 |
|---|---|
| 게시글·댓글 읽기 | 로그인된 사용자, 활성 글 목록 20개·댓글 목록 30개 조회 한도 |
| 게시글·댓글 작성 | 로그인 UID가 작성자 UID와 같고 필드·길이·서버 시각이 유효한 경우 |
| 게시글·댓글 내용 수정 | 해당 문서의 작성자만, 내용과 수정 시각만 변경 |
| 삭제 | 글 작성자만 영구 삭제 표식으로 전환, 댓글은 작성자만 삭제 |
| 좋아요 | 자신의 UID만 추가·제거, 다른 UID·내용·작성자 변경 불가 |
| 계정별 취향 읽기·쓰기 | 자신의 `users/<UID>/preferences/current` 문서만, 허용 필드·서버 시각 검사 |
| 취향 문서 삭제 | 거부, 초기화는 문서의 항목을 비움 |
| 계정별 학습 모델·기록 | 같은 취향 문서의 학습 항목, 본인만 접근하며 버전·차원·표본/로그 한도 검사 |
| 다른 컬렉션 | 기본 거부 |

게시글 제목 100자, 본문 5,000자, 댓글 2,000자, 닉네임 50자를 제한한다.
여러 줄 본문은 허용하며 공백만 있는 내용, 추가 필드, 작성자·작성 시각 위조는 거부한다.
좋아요 배열은 중복과 1,000개 초과를 거부한다. 그 이상의 규모에는 사용자별 하위 컬렉션으로 모델을 변경해야 한다.
게시글 삭제는 내용이 비워진 영구 ID 예약을 남긴다. 댓글 하위 문서는 자동 삭제되지 않지만 읽기·새 쓰기를 막고 기존 댓글 작성자의 정리는 허용한다. 삭제 ID 재사용과 복원을 차단한다.
댓글 수와 계정별 30초/5초 간격·24시간 20개/100개 작성 한도는 콘텐츠와 같은 원자적 쓰기에서 검증한다. 기존 데이터 이관과 구버전 제한은 [게시판 보안 보완](BOARD_SECURITY.md)을 참조한다.

## 재현

Node.js 24, Java 21:

```sh
cd tools/firebase_rules
npm ci
npm test
```

Windows에서 Java 경로가 없다면 실행 전에 Android Studio의 JBR 등 Java 21 경로를 `JAVA_HOME`으로 지정한다.
테스트는 `demo-bobpool`, `127.0.0.1:8086`에서만 실행한다. 실제 계정이나 프로젝트 키가 필요하지 않다.
권한 테스트에서 작성자 허용, 다른 계정의 수정·삭제 차단, 작성자 위조, 좋아요 조작, 필드·길이·시각 경계,
삭제된 부모 문서, 취향 계정 격리·스키마·초기화·두 클라이언트의 동시 트랜잭션, 기본 거부를 확인한다.
테스트 로그의 `PERMISSION_DENIED`는 거부 케이스의 기대 결과다.

## 실제 Firebase에 적용할 때

2026-10-12 게시판 보안 보완 소스 `4848f33b85d2bd94e301d9ed326b7cd0765b2543`의 규칙을 실제 `bobpool-89802`에 적용했다. 두 조회 인덱스의 READY 상태, 서버 규칙과 소스 일치, 글 5개·댓글 2개의 상태/집계 이관 완료를 확인했다. 구버전 APK의 게시판 요청은 제한되므로 [새 연결 APK](APK.md)로 업데이트해야 한다. 실제 운영 콘텐츠를 새로 작성·삭제하는 테스트는 수행하지 않았다.

2026-10-12 소유자의 명시적 승인으로 `values.learning`에 본인의 학습 모델·반응 기록을 저장하는
규칙을 `bobpool-89802`에 적용했다. CLI에서 컴파일·Firestore release·배포 완료를 확인했다.
학습 소스 커밋 `3b558d18a069968c8b537700f361e75b9de65634`의 GitHub CI 두 작업도 성공했다.
실제 사용자 계정의 화면 저장·학습 반영 검증은 규칙 배포와 별도로 확인해야 한다.

2026-10-11 서버 저장 변경에서는 `users/<UID>/preferences/current`의 본인 읽기·쓰기를 추가한 규칙을
`bobpool-89802`에 배포했다. 기존 게시판 권한을 유지하며, 기기 기록 이관은 규칙 배포 때가 아니라
업데이트된 연결 모드 앱에서 해당 계정의 첫 취향 읽기·쓰기 때 실행된다.

검증한 규칙을 Firebase Console의 Firestore 규칙 탭에 적용하거나 아래 명령을 사용한다.
기존 규칙을 먼저 백업하고, 실제 프로젝트 ID를 명시해서 대상 혼동을 피한다.

```sh
firebase deploy --project <내-프로젝트-ID> --config firebase.dev.json --only firestore:rules
```

이 테스트 통과만으로 현재 운영 서버의 권한이 보호된다고 주장하지 않는다.
현재 실제 적용·확인 상태는 [검증 기록](VERIFICATION.md)에 기록한다.

2026-10-11에는 소유자의 승인으로 기존 규칙을 백업한 뒤 새 규칙을 실제 프로젝트에 배포했다.
비로그인 읽기의 HTTP 403 응답을 확인했다. 저장소를 복제해 실행하는 경우에는 자신의 프로젝트에
별도로 배포해야 한다. `createAt`만 있는 과거 테스트 문서는 새 구조에 맞게 검토·변환해야
수정과 좋아요를 사용할 수 있다. 규칙 배포 자체가 데이터 마이그레이션을 수행하지는 않는다.
