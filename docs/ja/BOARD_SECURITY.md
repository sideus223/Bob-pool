# 掲示板の読み書き・削除の制御

ページ取得、アカウント別投稿制限、削除状態、アクセス権限を管理します。

<br><br><br>





## 取得範囲

- 掲示板と自分の投稿は`deleted == false`を対象に、作成時刻と文書IDで並べて20件ずつ取得します。
- コメントは作成時刻と文書IDで並べて30件ずつ取得します。同時刻の記録もIDで区別します。
- スクロール／追加読み込みで次ページ、引っ張る操作／投稿・詳細画面からの復帰で更新します。全一覧のリアルタイム購読は使いません。
- 詳細投稿1文書のリアルタイム購読は維持します。コメント本文はページ取得し、件数は親の`commentCount`から読みます。
- ルールも明示的な上限（投稿20、コメント30）を要求し、アプリ外からの無制限一覧取得を拒否します。

コメント数は取得ページの長さではありません。コメント作成・削除と親の正確な±1変更を同じ原子的操作で行い、対象ID・作者・時刻・実際の作成／削除をルールで確認します。件数だけの変更や、1回の増加による複数コメント作成は拒否します。

<br><br><br>





## アカウント別の投稿制限

| 種類 | 最小間隔 | 24時間窓の最大作成数 |
|---|---:|---:|
| 投稿 | 30秒 | 20件 |
| コメント | 5秒 | 100件 |

最初の投稿の**サーバー時刻**から始まる24時間窓で、韓国時間の午前0時にリセットする方式ではありません。`users/<UID>/boardLimits/posts`と`comments`に開始時刻・最後の時刻・回数・正確な対象IDを記録します。コンテンツと制限記録を同じトランザクションで保存し、`getAfter`で両方を検査します。

制限記録なしの作成、記録だけの変更・削除、他人のUIDへのアクセス、時刻・回数の偽造、24時間前のリセット、最小間隔前の投稿、1記録による複数文書作成、対象ID不一致、旧許可の再利用を拒否します。

アプリ側の時刻検査は案内用で、サーバーの`request.time`の代わりにはなりません。複数アカウントによる乱用、制限内の反復読み取り、プロジェクト全体の費用上限は別の運用課題です。App Check、登録方針、費用警報も別設定です。

<br><br><br>





## 削除とID予約

作者の削除時は親文書を消さず`deleted: true`にし、タイトル・本文・ニックネーム・いいね・コメント数・直近コメント変更情報を空にします。UID・作成時刻・削除時刻はID予約と権限検証のため保持します。

削除済み親の変更・復元・いいね・物理削除、同じIDへの新規上書きは拒否します。コメントの読み取り・作成・変更も拒否しますが、元の作者が自分の既知のコメントIDを削除して整理することは許可します。削除印はログイン済みユーザーが読めるため、詳細画面で削除状態を表示できます。

既に開いた画面、端末キャッシュ、ユーザーのコピーの遠隔削除ではありません。コメント下位文書のサーバー整理は別の運用作業です。

<br><br><br>





## 移行と配布

旧投稿には`deleted`と`commentCount`がないため、新一覧の配布前に移行が必要です。親の物理削除後にコメントだけ残ったパスも削除印で予約します。

```sh
node tools/firebase_rules/migrate_board.mjs --project <project-id>
# 既定は読み取り専用dry-run。変更数のみ出力し、本文や認証情報は出力しない。
```

既存Firebase CLIのログイン権限を使い、秘密鍵は追加しません。`--apply --confirm-project <same-id>`を指定した場合だけ変更します。原子的トランザクションと以前の更新時刻の条件を使い、変更前データはGit対象外の`tmp/board-migration/<timestamp>/before.json`に保存します。

元の本文・作者・時刻は維持し、有効状態と実コメント数を追加します。孤立コメントを復元せず、欠落した親IDを予約します。`createAt`などの古い不完全文書について、時刻や作者を自動推定しません。

準備順はインデックス→新ルール→移行と再取得→新APKです。旧APKの無制限一覧・投稿・物理削除は新ルールで拒否されるため更新が必要です。推薦・好み文書の構造と権限は維持します。

<br><br><br>





## 検証

分離した`demo-bobpool` Emulatorで正常投稿、所有権、取得上限、間隔・回数、同時要求、バッチ迂回、削除後復元、コメント集計偽造を確認します。Flutterではページサイズ、同時刻カーソル、自分の投稿範囲、トランザクション、遅延応答、再試行を確認し、移行計画は別の純粋関数テストで確認します。

テスト範囲は[検証記録](VERIFICATION.md)、APKは[接続版・デモ](APK.md)を参照してください。Emulator成功は実アカウントで運用投稿を作成した証拠ではありません。
