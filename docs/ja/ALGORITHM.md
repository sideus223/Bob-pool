# 推薦アルゴリズムの設計

![推薦アルゴリズムと個人の反応学習](../images/recommendation-algorithm-ja.png)

[スコア・繰り返し・抽選確率の詳細図](../images/recommendation-details-ja.png)・[学習の詳細図](../images/learning-model-ja.png)

推薦記録は`policyVersion=3`を使用します。モデル・推薦・反応はアカウント別に保存します。[保存構造](SERVER_PREFERENCES.md)・[APK](APK.md)

必須条件→好みのスコアと学習補正→確率抽選→反応学習の順に処理します。計算はアプリ内、接続モードの記録はFirestoreです。説明可能な規則に個人別ロジスティック回帰を追加した構成で、重みは初期設計値です。実ユーザーの推薦精度は測定していません。[学習モデル](LEARNING_MODEL.md)

<br><br><br>





## 入力と必須条件

- 気分5種、シーン6種、辛さ4種（指定なしを含む）、最大予算5,000〜50,000ウォン。
- 有効価格は`0 < budgetMin <= budgetMax`。候補の`budgetMax <= 入力予算`を要求します。
- 辛さは指定なし以外、完全一致が必要です。
- 個別再推薦の同じセッションで表示済みのメニューと、気分別設定で明示的に除外したメニューは候補から外します。
- 否定反応は候補に残してその気分で大きく減点します。
- 候補0件なら空の結果を返し、予算・辛さを自動で緩めません。

価格はデータセットの推定値です。実店舗の現在価格を保証しません。原版の`budgetMin <= budget <= budgetMax`では予算増加で安いメニューが落ちましたが、本アルゴリズムは価格上限を比べます。

## スコア

| 項目 | 点数 | 意味 |
|---|---:|---|
| 気分一致 | +12〜+30 | 基本+30。十分な両反応で縮小、明示的追加は+30維持 |
| シーン一致 | +10〜+25 | 基本+25。十分な両反応で縮小 |
| お気に入り | +20 | いいねで保存したメニュー |
| 気分に明示的に追加 | +15 | ユーザーによる関連付け |
| 選択履歴 | +5／回、最大+15 | 選択ボタンで確定した回数 |
| 好みではない | -60 | その気分の否定反応。候補は維持 |
| 最近の推薦 | -20 | 24時間以内に表示したメニュー |
| 最近の選択 | -50 | 48時間以内に選択したメニュー |
| 先週の選択 | -20 | 48時間以上、7日未満の選択 |
| 最近の類似料理 | -12 | 24時間以内の最後の推薦と同じ形態。一部は調理法も一致 |
| 初期学習補正 | 最大±6 | 4標本・2メニューから。一方の反応のみならその方向のみ |
| 十分な反応の補正 | 最大±30 | 8標本・肯定／否定各1件・3メニュー以上 |

十分な反応では`c = min(標本数 / 24, 1)`とし、基本タグを`1 - 0.6c`倍して丸め、補正は`round((2p - 1) × 30 × c)`です。初期補正と大きい補正は足し合わせません。無効化または適用条件未達なら基本タグを維持します。

総点降順、同点なら表示記録なし→最後の表示が古い→累計表示が少ない→メニューID順に並べます。計算・診断用の順序であり、最終選択は抽選です。Softmaxは同点に同じ確率を与えますが、探索を加えた最終確率は履歴により異なる場合があります。同じ入力・履歴・時刻では同じスコアと確率になります。テストは固定乱数シードを使います。推薦理由は推薦時のスナップショットで、評価点や満足確率としては表示しません。

否定-60と明示的除外は異なります。初期化まで維持し、気分に再追加するとその気分の否定も消します。アレルギー・材料フィルターではありません。必須条件を先に検査するため、高いスコアでも違反しません。

推薦と選択の減点は併用できます。24時間・48時間・7日で解除／緩和し、未来時刻は無視します。候補を除かないため、1候補なら減点されても推薦されます。

## 確率への変換

すべての適格候補にSoftmax、温度`T = 10`を使い、上位だけに切りません。

```text
s(i) = exp((score(i) - maxScore) / T)
       / sum(exp((score(j) - maxScore) / T))
p(i) = 0.9 * s(i) + 0.1 * exploration(i)
```

最大スコアの減算は指数のオーバーフローを防ぎ、全スコアが負でも計算できます。温度は正の有限値です。小さいと最高点に集中し、大きいと分散します。60・50・40点の純Softmaxは約66.52%・24.47%・9.00%、3候補すべてが最少表示の探索対象なら約63.21%・25.36%・11.44%です。満足確率や推薦精度ではありません。

探索対象は必須条件を満たし、その気分で否定なし、学習補正が非負、24時間以内の推薦なし、7日以内の選択なし、直近の類似料理ではないメニューです。その中で表示回数が最少の候補に10%を均等配分します。探索候補がなければ純Softmaxを使い、除外や条件違反を探索に戻しません。

ほかの点が同じなら、否定-60のSoftmax重みは通常候補の`exp(-60 / 10) ≈ 0.00248`倍で、探索確率は加えません。実確率は全候補次第で固定値ではありません。全候補に同じ減点なら相対確率は変わらず、1候補なら100%です。同じ再推薦セッションの表示済みメニューは除外します。

初回・再推薦・旧互換サービスは`LocalRecommendService.pick`を通ります。候補計算と抽選だけでは保存せず、結果画面に接続したときに表示を記録します。低スコアが選ばれても実際の点数寄与・理由を渡します。

## 類似料理の繰り返し

全メニューと履歴から最近24時間の最後の推薦を探します。その料理が現在の候補から外れていても比較します。麺・スープ・パン・サラダは形態一致、ご飯・一品料理・軽食・その他は形態と調理法の両方一致で-12点です。同一メニューは既存の最近推薦の減点を使い、類似減点を重ねません。古い／未来の記録は使いません。

類似候補を除去せず、すべて似ていても推薦できます。探索対象がなければ純Softmaxです。完全な連続禁止ではありません。ランダムモードではこの調整を使いません。

## 反応と保存

表示は推薦回数と最後の推薦時刻、選択は選択回数と最後の選択時刻です。候補計算だけでは記録せず、結果画面への進入と再推薦の結果置換で表示を記録します。レシピから戻る、再描画するだけでは増やしません。ランダムの表示・選択も将来の個別推薦用に記録しますが、ランダムの候補計算自体は使いません。

選択回数は選択ボタンだけで増やし、同じ結果画面の重複操作を防ぎます。再進入して選ぶ場合は別の選択です。デモのキーは`bap_pool_v2_<scope>_<item>`、接続版は`users/<UID>/preferences/current`を基準にトランザクションで変更します。文書がない場合だけ同じUIDの旧ローカルを移行します。デモscopeは`demo`、実アカウントはUIDです。書き込みは直列化し、途中のアカウント変更を拒否します。所有者不明の旧共通キーは移行・削除しません。

`interaction_history`に回数と時刻をまとめ、デモはJSON、接続版はFirestore mapです。旧`selections`は初回記録時にコピーして元データを残し、過去の選択時刻は推定しません。破損JSON、負の回数、範囲外時刻は無視して推薦を継続します。[サーバー保存](SERVER_PREFERENCES.md)
