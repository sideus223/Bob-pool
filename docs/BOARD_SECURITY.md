# 게시판 데이터와 권한

게시판의 페이지 조회, 계정별 작성 제한, 삭제 상태와 접근 권한을 관리합니다.

<br><br><br>





## 조회량

- 게시판과 내 글: `deleted == false`, 생성 시각과 문서 ID로 정렬하고 20개씩 커서 조회한다.
- 댓글: 생성 시각과 문서 ID로 정렬하고 30개씩 조회한다. 같은 시각의 기록도 ID로 구분한다.
- 다음 페이지는 스크롤 또는 더 불러오기, 갱신은 아래로 당기기 또는 작성·상세 화면에서 돌아왔을 때 수행한다. 목록 전체의 실시간 구독은 사용하지 않는다.
- 상세 게시글 한 문서의 실시간 구독은 유지한다. 댓글 본문 목록은 갱신·페이지 조회하며, 댓글 수는 부모의 `commentCount`를 읽는다.
- 규칙에서도 명시적인 조회 한도(게시글 20, 댓글 30)를 요구한다. 앱 밖에서 무제한 목록 조회를 요청하면 거부한다.

댓글 수는 조회한 페이지 길이가 아니다. 댓글 생성·삭제와 부모의 정확한 ±1 변경을 같은 원자적 작업에서 처리하고, 규칙은 변경 대상 댓글 ID·작성자·시각·실제 생성/삭제를 확인한다. 숫자만 수정하거나 한 번의 증가로 여러 댓글을 생성할 수 없다.

<br><br><br>





## 계정별 작성 제한

| 종류 | 최소 간격 | 24시간 창의 최대 작성량 |
|---|---:|---:|
| 게시글 | 30초 | 20개 |
| 댓글 | 5초 | 100개 |

첫 작성의 **서버 시각**에서 시작한 24시간 창이다. 한국 시간 자정에 초기화되는 달력 기준은 아니다.
각 UID의 `users/<UID>/boardLimits/posts`와 `comments`에 시작 시각·최근 작성 시각·개수·정확한 대상 ID를 기록한다.
작성과 제한 기록을 트랜잭션으로 함께 저장한다. 규칙은 `getAfter`로 양쪽을 검사해 다음을 거부한다.

- 제한 기록 없이 콘텐츠 생성, 제한 기록만 단독 변경·삭제, 다른 UID의 제한 접근.
- 시각·개수 위조, 24시간이 지나기 전 초기화, 간격 이전 재작성.
- 한 번의 제한 기록으로 여러 문서 생성, 대상 ID 불일치, 이전 허가 재사용.

앱의 시간 검사는 안내용이며 서버의 `request.time` 검사를 대체하지 않는다. 여러 계정을 만드는 남용이나 반복적인 제한 내 읽기, 프로젝트 전체의 비용 상한까지 해결하는 정책은 아니다. App Check·가입 정책·비용 경보는 별도 운영 설정이다.

<br><br><br>





## 삭제와 ID 예약

작성자가 삭제하면 부모 문서를 제거하지 않고 `deleted: true`로 유지한다. 제목·본문·닉네임·좋아요·댓글 수와 최근 댓글 변경 메타데이터를 비운다. UID·생성 시각·삭제 시각은 ID 예약 및 권한 검증을 위해 남는다.

삭제된 부모는 다시 수정·복구·좋아요·물리 삭제할 수 없다. 동일 ID에 새 부모를 덮어쓸 수도 없다. 댓글 읽기·생성·수정은 차단되며, 기존 작성자가 알고 있는 자신의 댓글 ID로 삭제하는 정리는 허용한다. 삭제 표식 자체는 로그인한 사용자가 읽을 수 있어 상세 화면이 삭제 상태를 안내한다.

기존에 받아 둔 화면·기기 캐시·사용자의 복사본까지 원격 삭제하는 기능은 아니다. 댓글 하위 문서의 서버 정리는 별도 운영 작업이며 기존 소유자의 삭제 권한을 유지한다.

<br><br><br>





## 기존 데이터 이관과 배포

기존 글에는 `deleted`와 `commentCount`가 없으므로 새 목록 배포 전에 이관이 필요하다. 과거 물리 삭제 후 댓글만 남은 경로도 삭제 표식으로 예약해야 재사용을 막을 수 있다.

```sh
node tools/firebase_rules/migrate_board.mjs --project <프로젝트-ID>
# 기본은 읽기 전용 dry-run. 변경 개수만 출력하며 내용·인증 정보를 출력하지 않는다.
```

도구는 기존 Firebase CLI 로그인 권한을 사용한다. 개인키를 저장소에 추가하지 않는다. `--apply --confirm-project <동일-ID>`를 지정할 때만 실제 변경한다. 원자적 읽기/쓰기 트랜잭션과 문서의 이전 수정 시각 조건을 사용하고, 변경 전 자료는 Git에서 제외한 `tmp/board-migration/<시각>/before.json`에 보관한다.

이관은 기존 제목·본문·작성자·시각을 덮어쓰지 않고 활성 상태와 실제 댓글 수를 추가한다. 고아 댓글은 복구하지 않고 누락 부모의 삭제 ID 예약만 만든다. 기존의 `createAt` 오타 등 오래된 불완전 문서는 자동으로 생성 시각·작성자를 추정하지 않는다.

권장 순서는 인덱스 준비 → 새 규칙 적용(구버전의 제한 없는 쓰기 차단) → 이관과 재조회 → 새 연결 APK 배포다. 구버전 APK의 게시판 목록/작성/물리 삭제는 새 규칙에서 차단되므로 업데이트가 필요하다. 추천·취향 문서 구조와 권한은 유지한다.

## 검증

실제 운영 프로젝트와 분리한 `demo-bobpool` 에뮬레이터에서 정상 작성·소유권·조회 한도·간격/수량 제한·동시 요청·배치 우회·삭제 후 복원·댓글 집계 위조를 검사한다. Flutter 테스트는 페이지별 크기·같은 시각의 커서·내 글 범위·트랜잭션·지연 응답·재시도를 검사한다. 이관 계획은 별도 순수 함수 테스트로 검증한다.

테스트 범위와 APK 정보는 [검증 기록](VERIFICATION.md)과 [연결 APK](APK.md)를 참조한다. 에뮬레이터 성공은 실제 계정으로 운영 글을 작성했다는 뜻이 아니다.

구현은 [Firebase 원자적 규칙](https://firebase.google.com/docs/firestore/security/rules-conditions)과 [커서 페이지 조회](https://firebase.google.com/docs/firestore/query-data/query-cursors)를 따른다.
