# 추천 알고리즘 설계

![밥풀 추천 알고리즘과 개인 반응 학습](images/recommendation-algorithm.png)

[점수·반복 조정·확률 계산 상세 그림](images/recommendation-details.png) · [반응 학습 상세 그림](images/learning-model.png)

추천 기록은 `policyVersion=3` 형식을 사용합니다. 모델·추천·반응 기록은 계정별로 저장합니다. [저장 구조](SERVER_PREFERENCES.md) · [APK 다운로드](APK.md)

필수 조건 필터 → 취향 점수와 학습 보정 → 확률 추첨 → 반응 학습의 흐름입니다. 추천과 학습 계산은 앱에서 수행하고, 연결 모드에서는 계정별 기록을 Firestore에 저장합니다.

<br><br><br>





## 목표와 범위

필수 조건 → 취향 점수 → 상황 적합도 → 최종 제안의 흐름을
규칙 기반 추천과 개인별 로지스틱 회귀 학습으로 구현합니다.
추천 규칙과 [학습 모델](LEARNING_MODEL.md)의 적용 조건·점수·합성 평가를 설명합니다.
실제 사용자 추천 정확도 측정 결과는 없다.
가중치는 초기 설계값이며 사용자 실험으로 검증된 값이 아니다.

<br><br><br>





## 입력과 필수 조건

- 기분 5종, 상황 6종, 맵기 4종(상관없음 포함), 최대 예산 5,000~50,000원.
- 유효 가격: `0 < budgetMin <= budgetMax`.
- 최대 예산: **`budgetMax <= 입력 예산`**. 가격 범위 전체가 상한 이내여야 한다.
- 맵기: 상관없음 이외에는 정확히 일치해야 한다.
- 이미 본 메뉴: 맞춤 재추천 세션에서는 다시 제안하지 않는다.
- 기분별 관리에서 명시적으로 제외한 메뉴는 후보에서 뺀다. ‘별로예요’는 후보를 남기고 해당 기분에서 강하게 감점한다.
- 후보가 0개이면 빈 결과를 반환한다. 가격·맵기 제한을 자동으로 완화하지 않는다.

가격은 데이터셋 추정치다. 식당의 실시간 판매 가격을 보장하는 기능은 아니다.
기존 방식의 `budgetMin <= budget <= budgetMax`는 최대 예산이 증가할 때
저렴한 메뉴를 탈락시켰다. 이 알고리즘은 가격 상한을 비교하여 이 문제를 해소한다.

## 점수

| 항목 | 점수 | 의미 |
|---|---:|---|
| 기분 일치 | +12~+30 | 기본 +30. 충분한 긍정·부정 반응에 따라 점수 감소. 직접 추가한 기분은 +30 유지 |
| 상황 일치 | +10~+25 | 기본 +25. 충분한 긍정·부정 반응에 따라 점수 감소 |
| 찜 | +20 | 좋아요로 저장한 메뉴 |
| 기분에 직접 추가 | +15 | 사용자가 명시적으로 연결 |
| 선택 기록 | +5/회, 최대 +15 | ‘오늘은 이 메뉴’ 버튼으로 확정한 횟수 |
| 별로예요 | -60 | 해당 기분의 부정 피드백. 후보에서는 유지 |
| 최근 추천 | -20 | 최근 24시간 안에 결과로 제시한 메뉴 |
| 최근 선택 | -50 | 최근 48시간 안에 선택 버튼으로 확정한 메뉴 |
| 지난주 선택 | -20 | 48시간 이상, 7일 미만 전에 확정한 메뉴 |
| 비슷한 최근 메뉴 | -12 | 최근 24시간의 마지막 추천과 같은 음식 형태. 밥·일품·간식·기타는 조리법까지 같을 때 적용 |
| 초기 학습 보정 | 최대 ±6 | 표본 4개·메뉴 2개부터. 한쪽 반응만 있을 때는 그 방향만 반영 |
| 충분한 반응의 학습 보정 | 최대 ±30 | 표본 8개·긍정/부정 각각 1개·메뉴 3개 이상 |

충분한 반응의 신뢰 비중은 `c = min(표본 수 / 24, 1)`이다. 기본 기분·상황은 초기 점수에 `1 - 0.6c`를 곱해 반올림한다. 학습 보정은 `round((2p - 1) × 30 × c)`다. 초기 보정과 충분한 반응 보정은 동시에 합산하지 않는다. 학습을 끄거나 초기 적용 조건을 충족하지 못하면 기본 태그 점수를 유지한다.

총점 내림차순으로 정렬한다. 동점이면 **추천 노출 기록 없음 → 마지막 노출이 오래됨 → 누적 노출이 적음 → 메뉴 ID 순**으로 정렬한다.
이 정렬은 계산·진단을 위한 순서이며 최종 추천은 아래 확률 추첨으로 고른다. Softmax 부분은 같은 점수에 같은 확률을 부여한다. 탐색 부분은 노출 횟수와 최근 기록을 사용하므로 최종 확률은 동점이라도 다를 수 있다.
같은 입력·저장 기록·평가 시각은 같은 점수와 확률을 낸다. 테스트에는 고정 난수 시드를 주입한다.
추천 이유는 점수 계산 시 함께 생성하며, 평점이나 확률로 표시하지 않는다. 결과 이유는 추천 시점의 스냅샷이다.

‘별로예요’는 **-60점 감점**, 기분별 명시적 제외는 **해당 기분의 필수 제외**다. 초기화할 때까지 유지하며,
기분별 관리에서 직접 다시 추가하면 그 기분의 부정 피드백도 지운다. 알레르기나 재료별 필터는 아니다.
맵기·예산·명시적 제외 필터는 점수보다 먼저 적용되므로 높은 선호 점수나 확률 추첨으로 위반할 수 없다.

최근 추천과 선택의 감점은 함께 적용할 수 있다. 24시간·48시간·7일 경계에서 각 감점은 해제 또는 완화한다.
최근 기록은 후보를 없애지 않으므로 후보가 하나뿐이면 재추천할 수 있다. 미래 시각은 기기 시계 변경을 고려해 감점에서 무시한다.

## 점수에서 추첨 확률로

모든 필수 조건을 통과한 후보를 대상으로 **Softmax**, 기본 온도 `T = 10`을 적용한다. 상위 몇 개로 후보를 잘라내지 않는다.

```text
s(i) = exp((score(i) - maxScore) / T)
       / sum(exp((score(j) - maxScore) / T))
p(i) = 0.9 * s(i) + 0.1 * exploration(i)
```

최대 점수를 빼는 것은 확률을 바꾸지 않으면서 지수 계산의 오버플로를 방지한다. 음수 점수만 있어도 계산할 수 있다.
온도는 0보다 큰 유한값이어야 한다. 작을수록 최고 점수에 집중하고, 클수록 후보를 다양하게 추첨한다.
점수 60·50·40의 순수 Softmax 확률은 약 66.52%·24.47%·9.00%다. 세 메뉴 모두 같은 최소 노출 탐색 후보이면 최종 확률은 약 63.21%·25.36%·11.44%다. 이 값은 사용자가 좋아할 확률이나 추천 정확도가 아니다.

탐색 후보는 이미 필수 조건을 통과한 메뉴 중 해당 기분에서 별로예요가 없고, 학습 보정이 음수가 아니며, 24시간 안에 추천되거나 7일 안에 선택되지 않은 메뉴다. 비슷한 최근 메뉴도 탐색에서는 제외한다. 이 중 누적 노출 횟수가 가장 적은 메뉴끼리 10% 확률을 균등 배분한다. 탐색 후보가 없으면 순수 Softmax를 사용한다. 명시적 제외나 예산·맵기 위반 메뉴를 탐색으로 다시 넣지 않는다.

다른 점수가 같을 때 ‘별로예요’ -60점의 Softmax 가중치는 정상 후보 대비 `exp(-60 / 10) ≈ 0.00248`배다. 별로예요 메뉴에는 탐색 확률을 추가하지 않는다.
실제 확률은 전체 후보 점수에 따라 달라지며, 이 수치가 모든 부정 피드백 메뉴의 고정 확률을 의미하지 않는다.
모든 후보에 같은 감점이 있으면 상대 확률은 변하지 않는다. 후보가 하나뿐이면 감점이 있어도 100%로 선택된다.
이번 세션에서 이미 본 메뉴는 계속 제외하므로 ‘다른 메뉴 보기’에서 즉시 반복하지 않는다.

첫 맞춤 추천, 맞춤 재추천, 기존 호환 서비스 모두 `LocalRecommendService.pick`을 거친다.
후보 계산과 추첨은 저장 부작용이 없으며 결과 화면에 실제로 연결할 때 노출을 기록한다.
낮은 점수 메뉴가 선택되어도 그 메뉴의 점수 기여와 이유를 그대로 전달한다.

## 비슷한 음식 반복 조정

전체 메뉴와 계정 이력에서 최근 24시간의 마지막 추천을 찾는다. 그 메뉴가 예산·맵기·이번 세션 제외 조건으로 현재 후보에서 빠져도 비교에 사용한다. 면·국물·빵·샐러드는 같은 형태일 때, 밥·일품·간식·기타는 형태와 조리법이 모두 같을 때 -12점을 적용한다. 동일 메뉴에는 기존 최근 추천 감점을 적용하며 유사 종류 감점을 중복하지 않는다. 오래되거나 미래 시각인 기록은 사용하지 않는다.

비슷한 메뉴를 후보에서 제거하지는 않는다. 조건에 맞는 후보가 모두 비슷해도 추천을 계속할 수 있고, 탐색 후보가 없으면 순수 Softmax로 추첨한다. 종류 반복을 줄이는 정책이며 연속 반복을 완전히 금지하는 규칙은 아니다. 랜덤 모드는 이 조정을 사용하지 않는다.

<br><br><br>





## 피드백과 저장

결과 노출은 추천 횟수·마지막 추천 시각으로, 선택은 선택 횟수·마지막 선택 시각으로 구분한다.
후보 목록 계산만으로는 기록하지 않는다. 결과 화면 진입과 재추천 결과 교체 시 노출을 기록하고,
레시피에서 뒤로 돌아오거나 화면이 다시 그려지는 경우에는 추가 기록하지 않는다.
랜덤 결과의 노출·선택도 기록하여 이후 맞춤 추천에서 참고한다. 랜덤 후보 계산 자체는 이 기록을 사용하지 않는다.
결과 노출이나 레시피 열람은 선택 기록으로 취급하지 않는다. 사용자가 선택 버튼을
누를 때만 횟수를 저장하며 한 결과 화면에서 중복 누름을 막는다.
다시 진입해 같은 메뉴를 선택하면 별도의 선택으로 기록된다.

데모의 SharedPreferences 키는 `bap_pool_v2_<scope>_<항목>` 형식이다.
Firebase 연결 모드는 `users/<UID>/preferences/current` 서버 문서를 기준으로 읽고,
트랜잭션으로 수정한다. 서버 문서가 없을 때만 해당 UID의 기존 로컬 기록을 이관한다.
데모는 `demo`, 실제 계정은 Firebase UID를 사용한다. 쓰기는 순차 처리하고
요청 시작 시 계정 식별자를 캡처하며 연결 모드에서 계정이 바뀌면 작업을 거부한다.
이전 공용 키는 소유자를 알 수 없어 자동 이관하거나 삭제하지 않는다.
기분 초기화는 그 기분의 추가·제외·별로예요 기록을 지운다.

`interaction_history`에 횟수와 시각을 함께 저장하여 두 값의 부분 쓰기를 피한다.
데모는 JSON, 연결 모드는 Firestore 맵으로 저장한다. [서버 저장 정책](SERVER_PREFERENCES.md)을 참조한다.
기존 계정별 `selections` 횟수는 첫 기록 시 새 구조에 복사하되 원본은 보존하고 과거 선택 날짜는 추정하지 않는다.
잘못된 JSON·음수 횟수·유효 범위를 벗어난 날짜는 무시하여 추천 자체를 중단시키지 않는다.

## 파일과 검증

- `lib/services/recommendation_engine.dart`: 저장소에 의존하지 않는 순수 계산.
- `lib/models/recommendation_model.dart`: 입력·취향 스냅샷·점수·이유.
- `lib/services/local_recommend_service.dart`: JSON 캐시와 저장소 연결.
- `lib/services/softmax_sampler.dart`: 안정적인 확률 계산과 난수 주입 가능한 가중 추첨.
- `test/recommendation_engine_test.dart`: 명시적 제외·부정 피드백 감점, 최근성 시간 경계, 후보 소진, 데이터 검증.
- `test/softmax_sampler_test.dart`: 예시 확률, 음수 점수, -60점 상대 가중치, 낮은 점수 추첨, 숫자 안정성, 고정 시드 빈도 검사.
- 저장 테스트: 기존 횟수 보존, 계정 분리, 동시 기록, 손상된 기록 복구, 재추가로 부정 피드백 해제.
- 실제 데이터·화면 테스트: 별도 추천 요청 간 순환, 계산과 노출의 구분, 레시피 복귀 시 중복 노출 방지.
- 전체 UI 조건 **5 × 6 × 4 × 46 = 5,520조합**에서 모든 결과의 예산·맵기를 검사한다.

복잡도는 메뉴 수 N에 대해 필터·점수 계산 O(N), 정렬 O(N log N), 확률 계산·추첨 O(N)이다.
현재 100개 메뉴에 적합하며 계산 자체는 네트워크 없이 실행된다.
데모는 오프라인 사용이 가능하지만 연결 모드의 취향 읽기·쓰기는 인터넷 연결이 필요하다.

## 한계와 다음 실험

동점 후보는 같은 Softmax 확률을 가지지만 탐색 배분은 노출 이력에 따라 달라진다. 최근성 감점과 탐색은 반복 가능성을 낮추지만 별도 요청에서의 중복을 완전히 막지는 않는다.
적합도·찜 점수 차이가 크거나 후보가 적으면 같은 메뉴가 다시 나올 수 있다.
선택은 실제 식사 확인이 아니다. 24시간·48시간·7일 감점과 가중치는 실험 전 초기 정책이며 사용자 만족도 개선은 미측정이다.
랜덤 모드는 필수 조건과 개인화를 적용하지 않으며 UI에도 이를 명시한다.
